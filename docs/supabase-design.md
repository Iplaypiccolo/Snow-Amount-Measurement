# Supabase 구성 (snow-support 프로젝트)

> Cloudflare(D1 + Workers) 계획은 **Supabase로 대체**되었습니다. `docs/d1-schema-*.md/.sql` 은 설계 과정의 기록으로 남기고, 실제 표는 `supabase/migrations/` 가 기준입니다.

| 항목 | 내용 |
|---|---|

| 표 | 28개 (기준정보, 격자 편입, 기상 데이터, 장비 지원, 계정·기록) — `supabase/migrations/20261002_01_tables.sql` |

## 2. 역할과 권한 (서버 = DB 가 매번 검사)
| | 읽기 | 쓰기 |
|---|---|---|
| **비로그인** | **전부 차단** | 차단 |
| **관리자 admin** | 전부 | 기준정보·격자·적설·장비·지원 회차·계정 전부 |
| **피지원지사 branch** | 기준정보·장비·요청(타 지사 행 포함) | **본인 지사의 요청·편성 행만** (다른 지사로 옮기기·삭제 불가) |
| **지원장비 equip** | 기준정보·장비·요청 | 장비(vehicles, 회차별 지원 여부·일자·기관) |
| 비활성 계정 | **즉시 모두 차단** | 차단 |
| 임시 비밀번호 계정(`must_change`) | **내 계정 정보만** 볼 수 있음 → 비밀번호를 바꿔야 나머지가 열림 | 차단 |

- **관리자만** 읽는 것: 접속·수정 기록(`audit_log`), 계정 전체 목록, 수집 기록, 적설 업로드 기록, 설정. 지사·지원장비는 **자기 계정 1건**만 봅니다.
- **서버(수집 함수)만** 쓰는 것: 예보·특보·수집 기록. 관리자도 화면에서는 쓸 수 없습니다.
- 본인이 **자기 역할을 바꾸는 것은 불가능**합니다(계정 수정은 관리자만).
- 작성자·시각(`created_by`, `updated_by`, `by_user`)은 **DB가 채웁니다.** 화면이 값을 위조해서 보내도 무시됩니다.

## 3. 접속·수정 기록 (`audit_log`)
- 장비, 지원 회차, 회차별 지원 여부·일자, 지사 요청·편성, 지사·본부, 계정 변경 등은 **DB 트리거가 자동 기록**합니다. (누가=아이디·역할, 언제, 무엇=표와 키, **바뀐 값만** 전·후, IP)
- 바뀐 것이 없는 수정은 기록하지 않습니다. 수정자·수정시각만 바뀐 경우도 기록하지 않습니다.
- **고치거나 지울 수 없습니다.** 관리자, 서버(postgres), 비우기(TRUNCATE)까지 트리거가 막습니다. (1년 보관 후 정리 방법은 아래 "남은 일")
- IP는 요청 헤더(`cf-connecting-ip` → 없으면 `x-forwarded-for` 첫 값)에서 가져옵니다. 실제 Supabase 연결에서 헤더가 어떻게 들어오는지는 **계정 연결 후 확인**이 필요합니다.
- **로그인(접속) 기록**은 Supabase Auth 쪽에 따로 남습니다. 관리자 화면에서 보는 방법은 아직 정하지 않았습니다.

## 4. 시험 방법
`supabase/tests/rls_test.sql` 전체를 Supabase **SQL Editor**에 붙여넣고 실행합니다.
- 시험용 계정·자료를 만들었다가 **일부러 오류를 내서 전부 되돌리므로 실제 자료는 바뀌지 않습니다.**
- 결과는 오류 창에 `RLS 시험 결과 — 전체 103, 실패 0` 과 항목별 PASS/FAIL 로 나옵니다. **권한 규칙을 바꿀 때마다 다시 실행**하세요.

## 5. 무료 플랜 제약 (확인된 것)
- DB **500MB** (우리 자료는 수 MB~수십 MB, 로그는 1년에 30~60MB 안팎), 파일 1GB, 전송 5GB, Edge Function 월 50만 호출.
- **1주일간 사용이 없으면 자동 정지**(수동 복구 필요). 눈이 없는 여름에 주의 → 정기 호출 또는 유료.
- **자동 백업이 없음** → 정기 내보내기 필요.
- 암호 해시, 로그인 시도 제한, 세션은 Supabase Auth 가 담당합니다(직접 만들 필요 없음).

## 6. 계정 (완료)
| 계정 | 아이디 | 비밀번호 |
|---|---|---|
| 관리자1 | `admin-01` | 사용자가 대시보드에서 직접 만든 비밀번호(대화·저장소에 없음) |
| 관리자2 | `admin-02` | 임시 비밀번호(첫 로그인 때 변경) |
| 지사 59개 | `ex` + 지사 이름의 로마자 (예: `exchungju`, `exdongseoul`) | 임시 비밀번호(첫 로그인 때 변경) |

- 전체 목록은 `docs/accounts.md`. 로그인용 이메일은 `<아이디>@snow-support.invalid` 로 자동 생성한 **가짜 주소**이며 메일은 보내지 않습니다.
- **임시 비밀번호는 Storage `credentials` 버킷의 CSV 파일에만** 있습니다(채팅·저장소·DB 기록에 없음). 대시보드 → Storage → credentials 에서 내려받아 전달한 뒤 **파일을 삭제**하세요. 앱(API)으로는 관리자도 읽을 수 없습니다.
- 임시 비밀번호 계정(`must_change`)은 **비밀번호를 바꾸기 전에는 어떤 자료도 못 봅니다.** 바꾸면 DB 트리거가 자동 해제합니다.
- **아이디 로마자 표기**: 국립국어원 표기법(자음 동화 반영). 강릉 → `gangneung`, 대관령 → `daegwallyeong`.

### 가입 막기 (세 겹)
1. **대시보드 설정**: *Allow new users to sign up* 끄기 (사용자가 설정함. 제가 직접 확인할 도구는 없음)
2. **DB 권한(RLS)**: 가입만 한 사람(프로필 없음)은 **어떤 자료도 읽거나 쓸 수 없음** — `supabase/tests/accounts_check.sql` 로 확인(실제 자료가 있는 상태에서 0건)
3. **계정은 관리자만 만듦**: 함수 `account-admin` 은 관리자 로그인 토큰(또는 일회용 시작 토큰)이 있어야 동작

### 계정 발급 함수 `account-admin`
- 인증: 관리자 로그인 토큰(JWT) 또는 **일회용 시작 토큰**(15분 안에 한 번만, 해시로 저장 후 사용하면 삭제). 시작 토큰은 최초 대량 발급에 한 번 썼고 지금은 남아 있지 않습니다.
- 임시 비밀번호: 16자 무작위(소문자·대문자·숫자·기호 모두 포함 → 프로젝트의 비밀번호 규칙을 항상 만족, 헷갈리는 글자와 CSV 위험 글자 제외).
- 작업: `create`(최대 100개씩, 하나라도 입력이 틀리면 아무것도 만들지 않음, 실패한 계정은 되돌림) / `reset`(임시 비밀번호 재발급 + 모든 로그인 종료) / `disable`·`enable`(본인·마지막 관리자는 막음, 비활성화 시 로그인 즉시 종료) / **`set_passwords`**(관리자 화면의 엑셀표: 지사·지원장비 계정의 비밀번호를 관리자가 직접 정함. 관리자 로그인으로만 가능, 관리자 계정은 제외, 하나라도 규칙에 어긋나거나 같은 비밀번호가 겹치면 아무것도 바꾸지 않음, 기본은 `must_change` 다시 켬, 기존 로그인 종료, 비밀번호는 응답·기록에 남지 않음).
- 모든 작업은 접속·수정 기록(`audit_log`)에 남습니다. 비밀번호는 기록에 남지 않음(확인함).
- 비밀번호 규칙(12자, 소문자·대문자·숫자·기호, 아이디·지사 이름·반복·이어지는 글자 거절)은 서버(`core.mjs`)와 화면(`admin/policy.js`)에 **똑같이** 있고, `tests/test_admin_policy_parity.mjs` 가 5,000개 이상의 입력으로 비교합니다.
- 시험: `tests/test_account_admin.mjs` 17항목(가짜 DB·Auth). 실제 Supabase 에서는 계정 1개 시험 발급 → 59개 발급으로 동작을 확인했습니다. 함수는 **버전 3**(일괄 설정 포함)이 배포되어 있습니다.
- **관리자 화면에서 부르는 부분(로그인 토큰 경로)은 가짜 서버로만 시험**했습니다(`tests/test_admin_ui.py` 16항목). 실제 Supabase 에서는 병합 후 사용자가 로그인해서 처음 확인합니다.

### 관리 콘솔 (`admin/`)
로그인, 임시 비밀번호 강제 변경, 계정 관리, **비밀번호 일괄 설정(엑셀표)**, 접속 로그. 사용법은 `docs/admin-console.md`.

## 6-2. 알려진 경고 (보안 점검 도구)
- **유출 비밀번호 차단(Leaked password protection) 꺼짐**: Pro 플랜 전용 기능이라 무료에서는 켤 수 없습니다. 최소 12자 + 임시 비밀번호는 무작위로 보완합니다.

## 7. 남은 일 (다음 단계)
1. **로그인 화면 + 관리자 콘솔**(비밀번호 변경, 계정 초기화·비활성화, 접속 로그 보기) — 계정 발급 함수의 관리자 로그인 경로를 실제로 시험하게 됨.
2. **기준정보 이전**: `hierarchy.json`, `sections.json`, `stations.json`, 격자 편입 → 표. 화면용 요약본(`snapshots`) 생성.
3. **화면 연결**: 읽기부터(강설량·관할·격자 편입), 그다음 저장(관할·격자 변경, 적설 업로드), 장비 지원.
4. **로그인 화면**과 접속 기록 보기.
5. **백업 내보내기**(GitHub Actions 주 1회)와 **1주일 미사용 정지 방지**.
6. **예보·특보 수집**(Edge Function + 스케줄) — 먼저 공공데이터포털 API 접속 시험.
7. 오래된 `audit_log` 정리(1년 보관 후) 방법.

## 8. 보안 주의
- 브라우저에 넣는 키는 **공개 키(anon/publishable)**뿐입니다. **서비스 키(service role)는 HTML·저장소에 절대 넣지 않습니다.** (이 저장소는 공개입니다)
- 권한은 RLS 가 막습니다. 새 표를 만들면 **반드시 RLS 를 켜고 시험을 추가**하세요. (Supabase 보안 점검 도구가 RLS 없는 표를 알려 줍니다)
