# 일별 단기 보강 — SQL77 검토 (2026-11-06)

**운영 미적용.** 구역 연결 SQL76까지 적용돼 있다. 이번 단계는 가까운 날짜의 공식 최저/최고기온과 하늘 상태를 보관하는 기반이며, 일별 화면은 아직 기존2창이다.

## 검토할 SQL

[실행 원문](sql/forecast_daily_aux_77.review.sql). 기존 시간별 예보 표에 새 종류를 섞지 않고 비공개 보강 캐시 표1개를 추가한다. 기존5종 수집의 완료 판정,1시간·3시간 예보값/함수/예약을 변경하지 않는다.

- 저장 종류는SKY/TMN/TMX. **계획의 기본은TMN/TMX만**이며 SKY는 서버가 명시적으로 선택해야 한다. SKY 수집·오전/오후 대표 날씨를 지금 켜는 SQL이 아니다.
- 기존 발표의 격자 순서를 재사용하지만 보강 자료는 별도 표에 둔다. 같은 격자의 배열 위치가 발표마다 달라져도 해당 발표의 위치로 읽는다.
- 공식TMN은06시,TMX는15시 자료를 받는다. 이 시각의TMP가 아니라 별도 공식 최저/최고 항목이다. TMP의 최솟값을 일 최저로 대신하지 않는다. 서로 다른 시간대이므로 최저>최고도 정렬하거나 거부하지 않는다.
- 입력의0℃와 결측null을 구분한다. 새 빈 자료가 이미 받은 정상 배열을 덮지 않는다. 지점별 결측에는48시간 안의 이전 발표 정상값을 사용할 수 있고, 항목마다 발표시각을 함께 반환한다.
- 전국 원본이 실제 숫자 결측 격자인지 수집기가 확인한 경우만 빈 자료로 표시한다. HTTP/API 오류·시간초과를 빈 자료 성공으로 기록하면 안 된다. 빈 자료의 재확인은30분 간격·같은 발표/항목/시각당 최대3회다.
- 48시간 지난 **새 보강 캐시만** 정리한다. 기존 발표가 원래 정리될 때는 그 발표에 연결된 보강 자료도 함께 사라진다. 기존 업무/예보 자료를 추가 삭제하는 작업은 없다.
- 서버 역할만 계획/저장을 호출한다. 로그인 계정은 현재 유효 격자 한 칸의 공식 기온·원시SKY와 발표시각만 읽는다. 전국 원본 배열을 브라우저로 보내지 않는다.
- **이 SQL에는 자동예약·HTTP 호출이 없다.** 적용만으로 API 사용량이 늘거나 일별 화면이 열리지는 않는다. 이후 수집기를 연결한다. 사용자에게 발표/예보시각을 수동 지정하는 화면도 추가하지 않는다.

## 실제 자료 확인

읽기 전용 probe-daily-forecast v4를 시험 후 배포했다. 기존7종 점검은 유지하며 최신 단기 육상2종 조회와5개 격자 표본값 출력을 추가했다. 임의URL/구역/기간/키를 받지 않는다. 저장·예약은 없다. 익명 POST는 실제401로 거부됐다.

2026-11-06 20시 단기 발표와 날씨누리의 동일5km 격자 중심 좌표를 맞췄다. 서울60,127·대관령89,130·영암56,67·합천80,83·순천65,72의11/7 최저/최고10개 값이 모두 일치했다.0℃도 포함한다. [공개 대조 결과](research/forecast-daily-short-samples-20261106.json).

## 단기 육상 API 대안과 미확정 범위

공식 [단기예보 명세](https://apihub.kma.go.kr/apiList.do?seqApi=10&seqApiSub=286)의 fct_afs_dl.php/fct_afs_dl2.php는12시간 구간·하늘 상태·강수형태·기온·확률을 제공한다. 전국 일괄 자료가 일별 화면과 맞으면 시간별SKY 추가 수집을 줄일 가능성이 있어 읽기만 시도했다. 두 API 모두 ‘활용신청 필요’403이었다. 기존 구역정보 승인이 취소된 것이 아니며, SKY/TMN/TMX는 정상이다.

사용자는 ‘두 항목 활용신청 후 알려주기’를 선택했다. **신청 완료/승인 반영이라고 답한 것은 아니므로 아직 재조회하지 않았다.** 완료를 알려주면 기존 서버 키로 다시 확인한다. 새 키를 요청하지 않는다. 이 대안이 더 넓은 지역 단위이거나 발표/값이 맞지 않으면5km 격자 자료를 그대로 대체하지 않는다.

날씨누리 공개HTML의42개 완전한 반일 표본에서 단순 시간별 최댓값으로는 확률을 재현할 수 없었다. 예를 들어 영암 오전 시간별 최고20%인데 일별10%였고, 비가 있는 대관령 오전은60%였다. 비가 없는39개 구간에서는 평균을 사용하는 후보가 맞았지만 공식 산출식을 확정한 것은 아니다. 이 가설을 운영 코드에 넣지 않았다. 기존3시간 표의 최고 확률 계산도 변경하지 않았다.

## 사용량과 검증

- 최저/최고 기본 계획은02/05/08/11/14/17/20/23시 발표별8/8/7/7/7/8/8/8건, **기본61호출/일**이다. 재시도와 선택적SKY·분석 호출은 별도다. 고객 API 계정의 실제 잔여 한도는 확인하지 않았으므로 무조건 한도 안이라고 단정하지 않는다.
- 운영DB 크기는 조사 시104,429,235bytes였다. 이 SQL은 필요한 격자만 보관하고48시간 캐시를 유지한다. 전국37,697개 원본을 DB에 저장하지 않는다. 현재 보강 자료는 운영에0행이다(표 자체가 아직 없음).
- 로컬 PostgreSQL(PGlite)15/15: SQL 실제 실행, 기본계획61건/일, SKY 선택,0/null,발표별 배열 순서,늦은 결측의 정상값 덮기 방지,최저>최고,30분/3회 제한,48시간 캐시 정리,권한/RLS/로그인/유효 격자,기존 원자료/함수 유지.
- 점검 함수33/33·전체539/539(30묶음),511.5초·시험 중 프로그램 소스 변경 없음. 그 후 변경은 검토SQL·문서이며 프로그램은 동일하다. 이전 공개 구역 표본JSON의 잘못 붙은 선행+도 제거했고 자료값은 바꾸지 않았다.

추가 SQL 적용 전 원문 확인을 받는다. SQL77 이후는 보강 수집기 연결·실제 저장 확인,오전/오후 자료 대안 대조,중기와 결합한 일별 조회,PC3창/모바일1창3탭 순서다. 지난 오늘의 값이나 미제공 자료는 만들어 넣지 않는다.
