# 일별예보 구역 연결 조사 (2026-11-06)

현재 중기 수집·저장·자동예약75는 운영 중이다. 일별 화면은아직이며, 이번 단계는 선택한5km 격자를 중기 날씨/기온 구역과 연결할 근거를 확인하는 작업이다. 기존 예보·업무 자료를 변경하거나 새SQL을 적용하지 않았다.

## 확인한 기상청 선택 방식

같은 대관령 읍면동코드5176038000으로조회하되좌표만평창읍으로바꾸면, 가까운날단기예보는평창좌표에맞게바뀌지만중기기온은대관령으로유지됐다. 평창읍코드5176025000으로바꾸면같은좌표에서도중기기온은평창으로바뀐다. 이표본에서는중기구역을격자좌표의최단거리기온도시로바로고르면날씨누리와달라질수있다.

추가표본은현재기상청공식읍면동목록에서코드/좌표를받아날씨누리의중기6일최저/최고를서버의18시중기203도시원자료와대조했다. 각표본12개기온값이각각다음도시와일치했고중복일치도시는없었다.

## 공식 구역정보 API

`FcstZoneInfoService/getFcstZoneCd`는구역코드/명칭/위도/경도/상위구역/유효기간을제공한다. 공식명세와신청페이지: https://apihub.kma.go.kr/apiList.do?seqApi=10&seqApiSub=321

서버의읽기전용 `probe-daily-forecast` v3에 `kind:zones`를추가했다. 고정된공식API만조회하며페이지1~20·구역코드형식을검증한다. 전체목록페이지1 또는서울11B10101같은표본을조회할수있다.키는기존서버비밀값만사용하고,응답은좌표/상위구역등허용필드로한정한다. DB저장이나수집예약변경은없다. 기존6종점검은유지한다.

처음에는403 “활용신청이 필요한 API 입니다”였으나, 사용자의 최종 승인 답변 뒤 동일 서버 키로 재조회하여 **서울·도쿄 모두200을 확인했다. 이전403은 해결됐다.** 전체 목록은 페이지1에서755개, totalCount도755로 일치했다. 모든 반환 행의 종료일은210012310000이었다. 키를 로컬로 읽거나 사용자에게 추가 키를 요청하지 않았다.

## 승인 반영 후 연결 조사

추가 산간 표본도 각각 중기6일 최저·최고12개 값이 해당 도시와만 일치했다: 강릉 왕산면5115032000→11D20501 강릉, 평창 진부면5176036000→11D10503 평창, 양양 서면5183031000→11D20403 양양. 정선 고한읍처럼 다른 기온 도시가 더 가까워도 자기 시군구를 사용하는 사례가 있으므로 전국 최단거리만으로 연결하지 않는다.

일반 구역의 부모가 중기 육상 구역과 항상 같지는 않았다. 서울은11B10100→11B10000→11000000으로 이어지며 중기 통합11B00000을 거치지 않는다. 실제 육상 응답15개 구역과 별도 대조해야 한다.

현재 유효 격자1,538개 중 기존 지명으로1,500개 후보를 만들었다. 빠진 지명30개와 불완전한 시군구 표기8개를 조사해1,537개 후보까지 확보했다. 마지막59,122 산본동은 공식 군포시 읍면동 목록에서 산본1·2동 모두 해당 격자로 확인했다. 분석 자료는 작업공간 outputs/87_*에 보존했다.

**운영용 연결표로 확정한 것은 아니다.** 기존 지명은 OSM이며 인접 지명 대체가 포함된다. 후보 중 광역 이름만으로 선택한60칸은 공식 읍면동과 추가 대조해야 한다. 군위처럼 광역시 안에서도 기온 구역이 갈린다. 한5km 격자의 대표지점 선택과 노선 수정으로 새 격자가 생겼을 때의 연결 갱신도 구현해야 한다. 공식 목록755개는 행정 경계 폴리곤이나 공식5km 대응표를 제공한다는 뜻이 아니다.

프로그램 전체 시험 뒤 소스 지문이 동일함을 다시 확인했다. 승인 반영 후 변경은 조사와 문서뿐이라 전체518개 시험을 불필요하게 반복하지 않았다. 일별 화면은 아직 기존2창이며 새 SQL 작성·적용은 없다.
