# Cloudflare D1 표 설계 v1 (설계안 — 아직 Cloudflare에 만들지 않음)

코드 파일은 `docs/d1-schema-v1.sql` 입니다. SQLite 문법 검사를 통과하도록 시험했지만 **실제 Cloudflare D1에 올려서 확인한 것은 아닙니다.**
이 문서는 "어떤 정보를 어디에 어떻게 담고, 무료 한도 안에서 돌아가는가"를 사람이 읽고 확인하기 위한 것입니다.

## 0. 용어 (처음 보는 분을 위해)
- **D1**: Cloudflare가 주는 데이터베이스(엑셀 시트 여러 장이 서로 연결된 것). 한 장을 **표(테이블)**, 한 줄을 **행**이라고 부릅니다.
- **행 읽기 한도**: 무료는 하루 500만 행 "훑기"까지입니다. 100줄짜리 표에서 한 줄을 찾으려고 100줄을 모두 훑으면 100행으로 셉니다. 그래서 **인덱스**(색인)가 필요하고, 화면이 열릴 때마다 큰 표를 읽지 않도록 **요약본**을 둡니다.
- **요약본(snapshot)**: 화면용으로 미리 만들어 둔 JSON 한 덩어리를 한 줄에 저장해 두고, 화면은 그 한 줄만 읽습니다.

## 1. 확정된 원칙 (이 설계에 반영된 결정)
| 결정 | 설계에 미친 영향 |
|---|---|
| Cloudflare **무료 플랜만** | 모든 한도를 무료 기준으로 계산(아래 4번). 로그인 비밀번호 계산이 무료 CPU(10ms)를 넘을 수 있음 → 2단계에서 시험 |
| **운전원 정보 없음**(차량번호만) | 운전원·연락처 표 없음. 개인정보는 사실상 접속 아이디·IP뿐 |
| 수집 Worker는 **쓰기 전용**, 화면은 pages.dev 함수가 읽기 | Worker에 공개 주소 없음(보안 부담 감소) |
| 과거 시즌 적설은 **파일**, 올해 시즌부터 D1 | 큰 표를 매번 읽지 않음 |
| 전날 적설은 **내가 콘솔에서 받아 업로드**(자동 수집 제외) | Worker는 예보·특보만 수집 → 크론 1개 |
| 격자는 **지도에서 골라 기관에 편입**, 한 격자를 **여러 기관이 공유 가능** | `grid_assign`(격자-기관 다대다), 호출은 **합집합** 한 번씩만 |

## 2. 표 목록
### A. 기준정보 — 거의 안 바뀜 (관리자가 수정)
| 표 | 담는 것 | 규모 | 비고 |
|---|---|---|---|
| `hqs` | 본부(민자 포함) | 약 10행 | `is_private`=1 이면 관측소·적설 계산 안 함 |
| `branches` | 지사/기관 | 약 60행 | 번호(`B001`)로 연결 → 이름·본부가 바뀌어도 기록이 안 끊김 |
| `sections` | IC/JC 사이 관할 구간 | 1,011행 | 선 모양은 JSON 한 칸(행당 수 KB) |
| `jurisdiction_events` | 관할 변경 이력 | 수십 행 | 누가·언제·무엇을·사유 |
| `stations` | 적설관측소 좌표 | 약 680행 | 현재 저장소에는 배정된 260곳만 → 전체 목록 확보 필요 |
| `branch_stations` | 지사별 배정 관측소 | 약 330행 | 규칙(5km, 5대 이하면 6→8km)으로 계산한 결과를 저장 |

### B. 예보 격자 편입
| 표 | 담는 것 | 규모 |
|---|---|---|
| `grid_assign` | **(격자, 기관)** 짝. 한 격자에 기관 여러 곳 가능 | 1,000~수천 행 |
| `grid_events` | 편입 변경 이력 | 수십 행 |
| `warning_zones`, `cell_zone` | 특보 구역과 "격자 → 구역" 대응표 | 구역 수백, 대응표 수천 (제가 파일로 생성) |

### C. 기상 데이터
| 표 | 담는 것 | 쓰는 주체·주기 | 규모 |
|---|---|---|---|
| `snow_daily` | 관측소별 일 신적설 | 관리자 업로드, 하루 1번(약 680행) | 시즌당 약 8만 행 |
| `snow_uploads` | 업로드 기록 | 서버 | 하루 1행 |
| `forecast_cells` | 격자별 최신 24시간 적설 예보 | Worker, 하루 8번 | 편입 격자 합집합(≤수백) 행, **최신 1건만 덮어씀** |
| `branch_forecast` | 기관별 집계(최댓값과 그 격자) | Worker | 약 60행 |
| `warnings_active`, `warnings_history` | 발효 중 특보 / 끝난 특보 | Worker, 약 10분 | 수십~수백 / 계속 쌓임(적음) |
| `collector_state`, `collector_runs` | 나눠 실행 진행 위치 / 실행 기록 | Worker | 소량(오래된 기록은 정리) |
| `snapshots` | **화면용 요약본** (`reference`, `grid`, `snow:2026-27`) | 변경 때 서버가 다시 만듦 | 3~4행 (각 2MB 이하) |

### D. 장비 지원 — 운전원 정보 없음
| 표 | 담는 것 | 비고 |
|---|---|---|
| `equip_orgs`, `vehicles` | 지원 기관, 장비(차량번호·종류) | 차량번호가 곧 키 |
| `support_rounds` | **지원 회차**(눈 올 때마다 만드는 건) | 새로 넣는 개념. 지난 기록이 쌓임 |
| `round_vehicles` | 회차별 장비의 지원 여부(미정/지원/불가) | |
| `round_vehicle_days` | 지원 일자별 지원 기관(하루 여러 기관은 순서 `seq`) | |
| `round_requests` | 회차별 기관의 요청·편성 대수, 도착 시각, 사유 | |

### E. 보안·기록
`users`(계정, 비밀번호는 해시), `sessions`(로그인 상태, 쿠키 값의 해시만), `login_attempts`(실패 횟수 제한), `audit_log`(접속·수정 기록, **추가만**), `settings`.
- 아이디는 이름 대신 **기관코드+번호**(예: `gw-01`)를 권장합니다. 개인정보 부담이 더 줄어듭니다.

## 3. 화면(API)이 읽고 쓰는 길 — 지금 화면 코드를 거의 바꾸지 않기
서버가 D1에서 읽어 **지금 화면이 받는 JSON과 같은 모양**으로 돌려줍니다.

| 지금 화면이 읽는 것 | 서버가 돌려줄 때 | 읽는 행 수 |
|---|---|---|
| `hierarchy.json`, `sections.json`, `stations.json`, `jurisdiction_changes.json` | `snapshots['reference']` 한 줄 | **1행** |
| `snow_data.json` (과거 시즌) | 그대로 **파일**로 둠 | D1 사용 없음 |
| 올해 시즌 적설 | `snapshots['snow:2026-27']` 한 줄 | **1행** |
| 예보·특보(새로 생김) | `branch_forecast` + `warnings_active` | 약 300행 |
| 격자 편입(새로 생김) | `snapshots['grid']` 한 줄 | **1행** |
| `roads.json`(배경 도로) | 그대로 파일 | D1 사용 없음 |

쓰는 쪽:
- **일 적설 업로드**: 브라우저에서 파일을 읽고 검증한 뒤 서버에 보냅니다. 서버는 **JSON 한 덩어리를 한 문장으로** 넣습니다(바인딩 변수 100개 제한 때문에 한 행씩 넣으면 21문장이 필요한데, `json_each`를 쓰면 1문장). 올해 요약본은 **하루치만 더해서** 다시 씁니다(전체를 다시 읽지 않음).
- **관할·격자·장비 변경**: 변경 이력 표에 한 줄 추가 + 해당 표 갱신 + 요약본 재생성.

## 4. 무료 한도 계산 (대략)
| 항목 | 한도(무료) | 이 설계의 하루 사용량(추정) |
|---|---|---|
| 행 쓰기 | 100,000/일 | 적설 업로드 약 700 + 예보 약 2,900(300격자×8회 + 기관 집계) + 특보 변경분 수천 + 기록 약 2,000 → **약 1만 행 안팎** |
| 행 읽기 | 5,000,000/일 | 화면 열기가 요약본 1~3행, 예보·특보 약 300행 → 200명×5번 열어도 **약 30만 행** |
| 저장 용량 | DB당 500MB | 적설 시즌당 수 MB, 접속 로그 연 100MB 안팎(1년 보관 시) → 여유. 로그가 커지면 오래된 것을 파일로 보관 |
| 한 행 크기 | 2MB | 요약본(reference 약 0.8MB, 올해 시즌 약 0.3MB) 안쪽 |
| Worker 한 번 실행 | 쿼리·외부 요청 합쳐 50개 | 예보 수집은 한 번에 약 40격자씩 나눠 실행(300격자 ≈ 8번, 약 80분) |
| 한도 초과 시 | 쿼리가 멈춤(자정 UTC까지) | 읽기·쓰기 사용량을 관리자 콘솔에 표시하는 것을 5단계에서 고려 |

> 시험이 필요한 것: ① Worker의 CPU 10ms 한도에서 예보 응답을 분석할 수 있는지 ② 로그인 비밀번호 계산이 무료 CPU로 되는지 ③ 기상청 API 응답 형식(EUC-KR 등).

## 5. 아직 정하지 않은 것 / 나중에 확인
1. **격자 → 특보 구역 대응표**: 격자 중심점이 어느 시·군 특보 구역인지 판정할 경계 자료가 필요합니다. 구할 수 있는 자료에 따라 방법이 정해집니다.
2. **전체 관측소 목록**(좌표 포함): 기상청 API허브의 적설관측지점 목록을 받으면 `stations`를 채웁니다.
3. **지원 회차 운영 방식**: 회차를 누가 만들고 닫는지, 지난 회차를 어디까지 보여줄지.
4. 접속 로그(IP) 보관 기간과 오래된 로그 정리 방법.
5. 읽기 요약본을 **변경할 때마다 만들지, 일정 간격으로 만들지**.
